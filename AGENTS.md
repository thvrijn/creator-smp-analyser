# AGENTS.md

This file provides guidance to AI coding agents (Codex, Claude Code, etc.) when working with code in this repository.

## Project

CreatorSMP4 turns Minecraft livestream recordings (Dutch-language, "Creator SMP 4") into recaps: upload a stream video → transcribe it with faster-whisper → extract notable events with a local LLM (Qwen3-8B) → (planned) timeline and video builder.

**Language:** everything the user sees is Dutch: UI text, flash messages, error messages we write (also the worker's errors sent to the app) and the generated event titles/descriptions. Code, comments, logs and CLI output stay English. Minecraft/game terms (Nether, bastion, pickaxe…) may stay English. Internal keys stay English with Dutch labels in the UI (status values, event `type` via `eventTypeLabel` in `streamStatus.ts`). The Laravel locale is fixed to `nl` in `config/app.php`; `lang/nl` only holds the validation rules and pagination labels the app uses.

## The game: CreatorSMP Hardcore 4

What the analysis and the story are about (from the official explanation video and creatorsmp.nl, October 2026). 90 Dutch creators play one Minecraft hardcore world from 4 to 25 October 2026; after three weeks one player is left and wins. **Dead is dead**, except in the **grace period** (respawning is allowed in a player's first hour of play). A player may only be on the server while live on stream, so everything they do is on camera. The world is split by a big **wall** into team **Noord** and team **Zuid** (45 each; `teamId` per player, null = staff and extra accounts). The wall is closed in week 1; it holds **mazes** (doolhoven) that open at different moments, lead to the other side and to secrets, and are the domain of a **mysterious character and his henchmen**; a great **hall** in the middle opens for special occasions. The **Nether and End** are only reachable at random moments through one of the maze routes. There are remains of "previous inhabitants" in the world (lore). Generated chests can be looted by everyone individually. Whispers have a cooldown and delay, to push in-game interaction. Minecraft 26.2 (silver cave biomes); no spear and no mace. **Halfway** a second island opens: the **Verliezersrealm** (losers realm), where dead players get a second chance; three battle-royale rounds each give one winner a revive (3 players return to the main world). Both the losers' finale and the **grand finale** (25 October) are broadcasts. Jeremy Frieser is one of the organisers (he co-presents the explanation video). **creatorsmp.nl API** (unofficial and undocumented: what the site itself calls, found in its JavaScript; base `https://aap.creatorsmp.nl`, season 4 = event `27034f2e-08db-48e9-b3e4-2f947f6606e8`): `/api/events` (seasons), `/api/events/{id}/players` (players, socials, `teamId`, `serverId`), `/runtime/teams` (Noord, Zuid), `/runtime/servers` (Hardcore, Verliezers realm: where a player is), `/deaths` (time and death message), `/stats/history` (Minecraft statistics per player, one point per day, see "VOD sync" for why it cannot give join times), `/stats/snapshots/latest`, `/timeline` (the main events; empty so far), and `/api/announcements` (news, e.g. the finale in the cinema on 25 October). The user wants **4 recap episodes**: one per week and one for the finale.

## Data safety (from README — mandatory)

Never wipe or reset the database or volumes without explicit permission: no `migrate:fresh`, `db:wipe`, `docker compose down -v` or similar. Existing players, streams, transcripts and uploads must be kept. Add new migrations instead of editing old ones, and check existing data before deleting records, tables or volumes.

**Tests use a separate database:** the feature tests use `RefreshDatabase`, which wipes the database it runs against. `phpunit.xml` points them at `creatorsmp4_test` (in the same Postgres container) with both `<server>` and `<env>` set with `force="true"`. Both are needed: Docker injects `DB_*` as real environment variables, and Laravel reads `$_SERVER` first, so `<env>` alone silently falls back to the dev database. Don't remove these overrides. The same goes for `CACHE_STORE` and `QUEUE_CONNECTION` (Docker sets redis): without `force`, tests shared the dev Redis cache and could push jobs to the dev queue. If the Postgres volume is ever recreated, recreate the test database with `docker compose exec -T postgres psql -U creatorsmp4 -d creatorsmp4 -c "CREATE DATABASE creatorsmp4_test OWNER creatorsmp4"`.

## Commands

Everything runs in Docker Compose. Use the Makefile (`make help`):

- `make start`: the one command to get a working stack. It runs `up -d --build --wait` (layer cache, so it only rebuilds what changed), creates `creatorsmp4_test` if missing (`make test-db`), downloads the Whisper and event models into their caches (`make models`), and runs `scripts/check.sh` (`make check`: postgres, test DB, redis, migrations, app, queue, worker `/health`, GPU/CUDA). Keep this working whenever setup steps are added. `make stop` brings the stack down. `make start-lite` (or `NO_WORKER=1` with any target) starts everything except the local worker, for development without the NVIDIA GPU (laptop on battery): same `docker-compose.no-worker.yml` as macOS, stops a running worker container, skips `make models` and the worker/GPU checks. Jobs then wait for a worker, or run on a remote one that checks in. `make restart` stays without the worker while its container is not running. The `app` container runs `migrate --force`, `artisan serve` (:8000) and Vite dev (:5173, HMR) together.
- `make test`: Laravel feature tests (`php artisan test` in `app`). Run one test with `make test-filter FILTER='--filter=TranscriptionJobTest'` (or `--filter=test_method_name`).
- `make prompt-eval`: score the event-extraction prompt with the real model (see Architecture).
- `make worker-test`: all Python worker tests (`unittest discover` over `worker/test_*.py`). Run one file with `docker compose exec -T worker python3 -m unittest /worker/test_model_manager.py`.
- `make artisan CMD='...'`, `make migrate`, `make build` (Vite production build), `make shell`.
- `make logs-app` / `logs-queue` / `logs-worker`.
- `make remote-worker` (on a laptop/pc/Mac that works for the app elsewhere, e.g. the Pi): creates `worker/.env` from `worker/.env.example` on the first run, then builds and starts only the worker (`docker-compose.worker.yml`; native on macOS), downloads the models and checks that it answers on `WORKER_PUBLIC_URL` and checked in. On macOS `scripts/worker-mac.sh` reads `worker/.env` line by line (not sourced, so a value may contain spaces) and then listens on all interfaces (`WORKER_HOST`, default 0.0.0.0; the local dev worker without `worker/.env` stays on 127.0.0.1). `make remote-worker-stop` / `remote-worker-logs`. Don't run it next to the dev stack's own worker on the same GPU.
- `make user` (`php artisan user:create [--username= --name= --password=]`): create a login account, or set a new password for an existing username. There is no registration page. `AdminUserSeeder` (also called by `DatabaseSeeder`) adds the default admin account once (found by `User::ADMIN_EMAIL`, so also after a new username) and never overwrites it, so a changed password is kept. `make admin-reset` (`php artisan user:reset-admin [--username= --password=]`) puts a forgotten admin login back to admin/admin (or the given values; production asks for the password instead of using `admin`), creates the admin when missing and logs out its other sessions.
- `php artisan workers:list [--online]`: the registered workers and what they are doing.
- **Production / deploy** (setup in `DEPLOY.md`, same approach as `../uitzet-tracker-new`): the Raspberry Pi runs `docker-compose.prod.yml` from the checkout `/opt/docker/apps/creator-smp-analyser` (app on FrankenPHP as container `creatorsmp4`, port 8000 on the external Docker network `proxy` of the Pi's reverse proxy, no published ports; `QUEUE_WORKERS` queue processes; postgres; redis; no worker). The image comes from `docker/php/Dockerfile.prod` (assets built in a Node stage, `--no-dev`, `php artisan optimize` in `docker/php/entrypoint.prod.sh`) and is built on the Pi. `.github/workflows/ci.yml`: Laravel tests (Postgres service) and worker tests on GitHub's runners for every push/PR; a push to master then runs on the Pi's self-hosted runner (`[self-hosted, linux, ARM64]`, its own runner for this repo), which fetches with the run's token and calls `scripts/deploy.sh <sha>`. `deploy.sh` checks out the commit, builds the image while the old version runs, waits until no stream is `processing` (`DEPLOY_WAIT_MINUTES`, `FORCE=1`), backs up the database to `backups/` (kept: `DEPLOY_KEEP_BACKUPS`), migrates, runs `AdminUserSeeder` (only that seeder: `DatabaseSeeder` adds development data), and starts the new containers with `--wait`. It never removes volumes. Pull requests must never run jobs on the self-hosted runner (the repo is public). Keep the image building (`docker build -f docker/php/Dockerfile.prod .`) when adding PHP extensions or system tools, and keep `.env.production.example` in sync with new settings. The app trusts `X-Forwarded-*` from any proxy (`bootstrap/app.php`), because only the reverse proxy reaches it on the Pi.
- `make artisan CMD='db:seed --class=CreatorSmpPlayerSeeder'`: adds the 90 Creator SMP 4 players from creatorsmp.nl/spelers, with their Twitch logins and their photos downloaded from its CDN (source: `https://aap.creatorsmp.nl/api/events/{season 4 event id}/players`, `socials.twitchUrl`). Safe to re-run: existing players, photos and Twitch logins are kept, only missing ones are filled in. `DatabaseSeeder` calls it too. `CreatorSmpTeamSeeder` (team Noord/Zuid per player, `players.team`, only fills a missing team) and `CreatorSmpDeathSeeder` (`player_deaths`: time, death message, `source_id` = the id on creatorsmp.nl; `Player::deaths()`) hold data fetched **once** on 11 October 2026 and hardcoded: creatorsmp.nl's `robots.txt` shuts out AI crawlers (ClaudeBot, anthropic-ai, GPTBot…), so agents do not fetch the site or its API again; update these seeders by hand, or with the organisers' permission. Run both after the player seeder (`DatabaseSeeder` does; the deploy only runs `AdminUserSeeder`, so on the Pi run them once with `php artisan db:seed --class=…`).
- `php artisan stream:transcribe {id} [--sync]`: queue a transcription (or run it inline to debug) for an existing stream.
- Pint (`vendor/bin/pint`) is installed as a dev dependency. There is no JS lint or typecheck script.

## Architecture

Docker services: `app` (PHP 8.3 + Node: Laravel 12 + Inertia/Vue 3/TS, `PHP_CLI_SERVER_WORKERS=4`), `queue` (`queue:work redis`, timeout 3600s, `QUEUE_WORKERS` replicas, default 3, so a transcription on one worker does not hold up a job for another), `postgres`, `redis` (cache + queue), and `worker` (a Python HTTP server on :8001 that needs an NVIDIA GPU through the Container Toolkit; for CPU, set `WHISPER_DEVICE=cpu`, `WHISPER_COMPUTE_TYPE=int8`, `EVENT_DEVICE=cpu`).

**macOS** (detected by the Makefile, so always use `make` there): Docker cannot reach the Apple GPU, so the worker runs natively. The Makefile exports `COMPOSE_FILE=docker-compose.yml:docker-compose.no-worker.yml`, which leaves `worker` out of Docker; the native worker checks in as `mac-local` with `http://host.docker.internal:8001` (or with the settings in `worker/.env` when that exists). `scripts/worker-mac.sh` runs it from `worker/.venv` (built with `uv` from `worker/requirements-mac.txt`; `brew install ffmpeg uv` if missing), with Whisper and Qwen on Metal through MLX. Whisper: `WHISPER_DEVICE=mlx`, `mlx-community/whisper-large-v3-turbo` through mlx-whisper; `worker/mlx_whisper_model.py` gives it faster-whisper's `transcribe()` interface with the same Silero VAD (times mapped back with `SpeechTimestampsMap`), so `_transcribe_stream` is shared. mlx-whisper only decodes greedily (no beam search), which can loop over music (15× "Oh."), so a run of more than `MAX_REPEATS` (3) identical segments becomes one; `condition_on_previous_text=False` also stopped the loop but made the whole transcript less accurate. Measured on 10 min of stream 2 on the M4 Pro: MLX 21 s (29× realtime), faster-whisper on the CPU 157 s with 4 threads and 213 s with 8 (so `WHISPER_CPU_THREADS` stays at faster-whisper's default of 4). `WHISPER_DEVICE=cpu` falls back to faster-whisper (int8). Qwen: `EVENT_DEVICE=mlx`, `mlx-community/Qwen3-8B-4bit` through mlx-lm. Diarization: pyannote on MPS (`diarization.device()`; 5 min of stream 2 in 17 s, 154 s on the CPU, same speakers and embeddings), with `HF_TOKEN` from `worker/.env` or else `.env`. `requirements-mac.txt` pins torch/torchaudio 2.7.1 like Docker: pyannote 3.4 does not import with torchaudio ≥ 2.9 (`AudioMetaData`). mlx-lm needs transformers 5 and so huggingface_hub ≥ 1.0, which no longer accepts pyannote 3.4's `use_auth_token`, so `accept_use_auth_token()` passes it on as `token`. Stay on pyannote 3.4: 4.x has other voice embeddings, which would not match the other workers' voices. The worker logs to `storage/logs/worker.log` (`make logs-worker`), and `make restart`/`stop` restart/stop it too.

**Workers (registry):** the app never has a fixed worker URL. Every worker (the dev stack's `local-docker`, the native Mac worker, or a remote laptop/pc via `make remote-worker`) runs `worker/registration.py`: every 15 s it POSTs name, own URL (`WORKER_PUBLIC_URL`), backend/GPU/VRAM, capabilities (`WORKER_CAPABILITIES`, default `transcribe,extract`), priority (`WORKER_PRIORITY`, default cuda 100, mlx 50, cpu 10) and busy to `POST /api/workers/heartbeat` (`routes/api.php`, Bearer `WORKER_TOKEN`, checked by `VerifyWorkerToken`), and `POST /api/workers/offline` on SIGTERM/SIGINT. Without `WORKER_APP_URL` it does not check in. `workers` table / `App\Models\Worker`: online = heartbeat within `WORKER_ONLINE_SECONDS` (45). `App\Services\WorkerPool::claim($task, $stream)` locks and claims the best free, online, enabled worker with that capability (priority, then VRAM); one task per worker; `release()` in the jobs' `finally`. A worker the app cannot reach is marked offline (`markUnreachable`), so the retry picks another. A heartbeat with `busy=false` releases a claim older than `WorkerPool::STALE_CLAIM_SECONDS` (a killed queue job). Without a free worker a job sets the status to `waiting` ("Wacht op worker"; transcription stage `waiting_for_worker`), touches the stream and `release()`s itself every `WORKER_WAIT_SECONDS` (30): the jobs use `retryUntil()` (7 days, trait `App\Jobs\Concerns\WaitsForWorker`) plus `maxExceptions`, so waiting never uses up attempts. `waiting` counts as active in the controllers and `isStalled()` (a waiting stream that is not touched for 10 min lost its job). Audio: the app sends both `video_path` and `video_url`, a temporary signed route (`/api/worker-files/streams/{id}`, `signed:relative`, 12 h) prefixed with `WORKER_APP_URL`; a worker with the shared storage reads the file, any other downloads it into a temp file (stage `downloading_audio`, removed afterwards). The worker's own endpoints require the Bearer token when `WORKER_TOKEN` is set (401). `make start` generates `WORKER_TOKEN` in `.env` (`make worker-token`); a remote worker needs the same token in `worker/.env`. Settings (`/settings`) lists the workers (shared Inertia prop `workers`), can disable (`enabled`) or forget one; the header shows how many are online. Networking between the Pi and the workers: Tailscale (same names at home and away).

**Processing pipeline (spans PHP + Python):**

1. `StreamController@store` saves the uploaded video to the default disk (`storage/app/private`, max size from `config/streams.php`).
2. `POST /streams/{id}/transcribe` dispatches `App\Jobs\TranscribeStreamJob`. `App\Services\TranscriptionWorker` POSTs `{stream_id, video_path, video_url, ranges, hotwords}` to the claimed worker's `/transcribe` and reads back a **streaming NDJSON** response. Event types: `duration`, `stage`, `progress`, `segment`, `speakers`, `warning`, `completed`, `error` (stages: `downloading_audio`, `extracting_audio`, `transcribing`, `diarizing`). The job throttles progress writes into the `transcription_*` telemetry columns on `streams` (stage, progress, processed/duration seconds, ETA), then replaces all `transcript_segments` in one transaction.
   - **Whisper settings (measured 2026-10-11 on 20 min of stream 8, RTX 5060):** one speech piece at a time (`WHISPER_BATCH_SIZE=0`). Batched decoding (`BatchedInferencePipeline`, batch 8) was 33× realtime against 24×, but it decodes each 30 s piece in one pass and loses the rest when Whisper stops early: 5% fewer words and a 28 s stretch of conversation gone; batch 16 was no faster, 15 s pieces no faster than one at a time. Word times (`word_timestamps`) cost nothing measurable and are used to cut segments longer than 10 s after a sentence end (or a comma past 8 s) and to split segments by speaker. **Hotwords** (`TranscriptionWorker::hotwords`): the streamer, up to 20 players from their 10 earlier streams (`story_players` and speakers named after a player) and `config('season.hotwords')`, written as **one Dutch sentence**: Whisper copies its prompt's style, and a bare list of names gave 0 full stops and 6% fewer words on 10 min of stream 8 (a sentence: 286 full stops, words as without hotwords). They fixed "morog" → "Morrog" and never put a name where nobody said it (mlx-whisper, a port of OpenAI's Whisper, has no hotwords: with `WHISPER_MLX_INITIAL_PROMPT=1` (off by default) the Mac worker gets the sentence as `initial_prompt`, which starts each 5-minute chunk's previous text and slides out after ~220 tokens of speech, so it only helps the first minutes of every chunk, and Whisper can echo a prompt into the transcript over music; switch it on only after measuring on the Mac: `worker/hotwords_eval.py <audio> --start 13800 --length 600` compares with and without on the worker's own backend). Each 5-minute chunk is extracted with `WHISPER_CHUNK_OVERLAP_SECONDS` (30) extra; sentences that start in the overlap are left for the next chunk, which starts where the last kept sentence ends, so no sentence is cut at a chunk border. Known Dutch hallucinations (`HALLUCINATION_PATTERN`: Amara.org/"ondertiteld door" credits; not "Tamara", a player) and segments Whisper itself rates as no speech with low confidence are dropped.
   - **Speakers (diarization, `worker/diarization.py`):** after Whisper, pyannote (`pyannote/speaker-diarization-3.1`, `pyannote.audio` 3.4; 4.x needs torch 2.8) runs over the same extracted 16 kHz chunks, kept back to back (`read_audio` pads/cuts each to its nominal length, so `_audio_start` = chunk's place in the transcribed parts + Whisper time). Each segment gets the speaker with the most overlap (`transcript_segments.speaker`, null = none). A segment in which the speaker changes is split at the word where it changes (`split_by_speaker`: word times against the turns; runs under `DIARIZATION_MIN_SPLIT_WORDS`/`_SECONDS` (3 words, 1 s) are jitter and join a neighbour; a cut moves to punctuation at most 2 words away), sent as `segment_splits` (worker segment index → parts) in the `speakers` event; `TranscriptionWorker` replaces that segment by its parts. On 20 min of a conversation-heavy stream 19 of 307 segments held two speakers. pyannote 4 (`speaker-diarization-community-1`, torch 2.8) was tried on the same 20 min in a throwaway container (2026-10-11): 36 s vs 38 s, 2.1 vs 2.5 GB RAM, 3 speakers where 3.1 found 5 (two of them under half a minute); on the conversations both agree on most lines and each wins some disputed ones, so no clear gain for a torch upgrade and new voice embeddings. Speakers are numbered by speaking time, so 0 speaks the most: in a player's own stream almost always the streamer (the UI shows the player's name for 0, "Spreker n" for the others). It only says who speaks when, not who they are. The `speakers` event carries `segment_speakers` (indexed like the worker's `segment` events, so `TranscriptionWorker` keys segments by that index) and per speaker its speaking time and voice embedding, stored as `streams.transcription_speakers` for matching voices to players later (step 2). It is off without `HF_TOKEN` (gated models: accept hf.co/pyannote/speaker-diarization-3.1 and hf.co/pyannote/segmentation-3.0); a failure only sends a `warning` and keeps the transcript without speakers. pyannote is a third model in `ModelManager` (`diarization`), loaded after Whisper is released. Measured on the RTX 5060 laptop: a 3 h stream diarizes in ~6 min at ~2.9 GB RAM (20 min of audio: ~45 s). Two things keep that working: `MALLOC_MMAP_THRESHOLD_` in `worker/Dockerfile` (without it glibc never returned pyannote's batch tensors and a 3 h stream grew past 6 GB and was OOM-killed), and `DIARIZATION_MAX_CLUSTER_EMBEDDINGS` (clustering memory grows with the square of the embeddings). pyannote 3.4's checkpoints need `allow_checkpoint_classes()` under torch>=2.6 (`weights_only`). The event prompt does not use speakers yet. **Corrections** (`App\Services\StreamSpeakers`, `SpeakerController`, the speaker bar and per-segment speaker menu in the Transcript tab; a speaker chip filters the transcript to that speaker, `?speaker=n`, with "Wie is dit?" to name them and "In gesprek" per line to see it in the whole conversation). A line's text can be corrected by hand (✎ or a double click, `PUT /segments/{id}/text`, `TranscriptSegmentController`): `transcript_segments.original_text` keeps what Whisper wrote (shown as "aangepast", and it can be put back); a new transcription replaces corrected lines too: a speaker can be named after a player or a free label (`stream_speakers`, unique per stream+speaker; a row with a player is a confirmed voice for step 2), merged into another speaker (segments move, `transcription_speakers` adds up the speaking time and averages the embeddings by speaking time, the name moves along when the target has none), and a single segment can move to another speaker, a new speaker number or none. A new transcription deletes the stream's `stream_speakers` (new numbers). A row with neither player nor label means "unknown, don't match". **Voice matching across streams (step 2, `App\Services\VoiceProfiles`):** a player's profile is the normalised mean of their known voices (speakers named after them by hand, plus speaker 0 of their own streams unless named otherwise; speakers under `VOICE_MIN_SECONDS` are skipped). An unnamed speaker (not 0) is shown as the player whose profile is closest (cosine) when ≥ `VOICE_MATCH_THRESHOLD` and `VOICE_MATCH_MARGIN` ahead of the next, each player once per stream and never a player already in it (source `matched`, shown with a `?` and a "✓ Klopt" button that confirms it). The profiles are cached forever and forgotten by model events (`StreamSpeaker` saved/deleted, `Stream` `transcription_speakers` changed or deleted, `Player` deleted) and in `StreamSpeakers::name()`. The default threshold (0.6) is not measured on real streams yet: `php artisan voices:evaluate` compares all known voices across streams and prints per threshold how many same-player pairs pass and how many different players get mixed up. **Recognising speakers by text (`App\Services\SpeakerTextMatches`, table `speaker_text_matches`):** when players talk together, the other player's words are in both streams at the same server time. `refresh($stream)` compares, in both directions with every other player's transcribed stream (with speakers) that was live at the same time, each non-streamer speaker's sentences (≥ `MIN_WORD_PAIRS` word pairs) with what the other stream's streamer (speaker 0 unless named otherwise, or named after that player) says within ±`TOLERANCE_SECONDS` (15); a sentence is a hit when ≥ `MIN_CONTAINMENT` of its word pairs are said there. It stores hits/compared per speaker and other stream. `matches()` picks a player at ≥ `MIN_HITS` (3) and `MIN_LEAD`× the next player, each player once, never the streamer or a player named in the stream. It runs as `MatchSpeakerTextJob` (unique per stream) after every transcription with speakers, after a merge, and after naming speaker 0 or a speaker as/away from the streamer; `php artisan speakers:match-text [ids]` (re)does it for existing streams. `StreamSpeakers::recognised()` puts text matches before voice matches (`matched_by` text/voice; voice skips text-matched speakers and players), and `VoiceProfiles::knownVoices()` counts text-matched speakers as that player's voice. **Same moment across streams (`App\Services\SharedMoments`, prop `shared_moments` per event on the stream page):** server time = `started_at` + `video_offset_seconds` + file time. An event is linked to another player's stream that was on air then (`ended_at` null = live) only when that player is in the moment: a speaker in its segments is them (`StreamSpeakers::players()`: named, voice-matched, or speaker 0 = streamer) or the title/description names them (whole word, names of 3+ characters), or the other way round for an event of theirs within `TOLERANCE_SECONDS` (30). Being live at the same time alone never links (most of the ~90 players are). The link opens their overlapping event (`?event=`), or else their transcript at that time (`?at=` seconds in the file: highlights the segment playing then).
3. `POST /streams/{id}/extract-events` dispatches `ExtractStreamEventsJob`. It splits the segments into parts that overlap (`EVENT_CHUNK_SECONDS`/`EVENT_CHUNK_OVERLAP_SECONDS`, 300/60 s: long enough to see a whole happening, small enough for 8 GB of VRAM; the old 90 s parts made every sentence an event), POSTs each part to `worker /extract-events` (plain JSON) with `context` (the streamer and every player name, so misspelled names are corrected) and per segment its speaker's name (`StreamSpeakers::list`: the streamer, a named or recognised player, or "Spreker n"), validates again, dedupes, and stores `events` linked to segments through the `event_transcript_segment` pivot.
   - **Story events only** (the user's goal: all streams together form one storyline of the roleplay server): players meeting, doing something together, arguing, betraying, fighting, killing, trading, discovering or building something that matters, roleplay plot. Never chat talk (subs, questions, real life) or routine gameplay alone (chopping trees, crafting, a tool breaking). Fewer, bigger events: one event covers a whole happening.
   - **Storyline:** the worker also returns a 1-3 sentence `summary` of what happens in the game in each part (empty when nothing does). The parts with a summary are stored as `streams.story_parts`, and at the end `POST /summarize-story` (parts + events + context) writes `story_summary` and `story_players`. The worker writes the story **per hour** (`EVENT_STORY_CHAPTER_SECONDS`, one paragraph each): one call over a whole stream's 70+ parts made the 8B model repeat the same sentence three times. Don't use `no_repeat_ngram_size`/`repetition_penalty` for this: in transformers they count the prompt too, so the model could not copy names and words from its input and misspelled them ("Zuit", "bespreeken"). Story players are matched to the server's player list (`known_player`: "Egbert"/"Ebertlive" → Egbertlive) and names that are nobody on the server (viewers who donated) are dropped. That is one extra progress step (`chunks_total` = parts + 1). A failed storyline only adds a note to `event_extraction_error`; the events are kept. The stream page shows it in the **Verhaal** tab (default tab when there is a story), with a summary per part (▶ and a transcript link).
   - **Grounding** (the model filled quiet parts with things it knows from Minecraft, e.g. "a secret in the Nether" on a server without a Nether, while the streamer said he was going to the toilet): every event gives a `quote` from its lines, and an event whose quote is not said there (word pairs, `quote_found`) is skipped. An event or summary sentence that names a place or thing from `GAME_TERMS` (Nether, End, bastion, portal…) that the transcript never says is dropped, and so are summary sentences about chat or the stream (`CHAT_PATTERN`) and sentences repeating an earlier one (`clean_text`). "Spreker n" stays in events and the story: the stream page shows it as a clickable name (`Components/SpeakerText.vue`, the current name once it is named or recognised) that opens the speaker editor (`Components/SpeakerEditor.vue`, also used inline in the Transcript tab) as a pop-up, with ▶ to listen from that moment. The prompt itself must not name such terms as examples: it used to say "Keep game terms in English (Nether, bastion…)", which primed them.
   - Validation rules (agreed with the user), applied on both sides: an invalid event is skipped and logged, never stored, and the rest of the chunk is kept. Event `start_time`/`end_time` are always derived from the referenced segments, never taken from the model (the prompt no longer asks for timestamps). An event needs at least `EVENT_MIN_SEGMENTS` (2: one line is a remark, not a happening) and at most `EVENT_MAX_SEGMENTS` (200: a roleplay talk can fill most of a 5-minute part; more is a summary of the whole part) segments.
   - Dedupe across overlapping chunks: events sharing at least half of the smaller event's segments are the same moment, whatever the title or type. The most confident one is kept. An event that starts within 60 s of an earlier one's end and shares ≥ 35% of its word pairs (title + description) continues it: a half-hour meeting is reported again in each next part, and becomes one event. An event over more than 80% of a part's lines (parts of ≥ 40 lines) is that part's summary, not a happening, and is skipped on both sides (`coversWholeChunk`): in long talks the model otherwise returned one such event per part.
   - The prompt (`SYSTEM_PROMPT` in `worker/event_extractor.py`) asks for story events only (see above), `first_line`/`last_line` per event (two numbers: listing every index of a long happening ran out of `EVENT_MAX_TOKENS` and broke the JSON; a `lines` or `segment_indexes` list is still accepted), and a `summary`. Titles must name the players involved, spelled as on the player list. Measure prompt changes with `make prompt-eval` (synthetic Dutch SMP chunks with speakers, known story moments and known noise lines: chat talk and routine gameplay; uses the GPU and restarts the worker). Pass a JSON of real chunks to also see real events and the storyline: export them like `ExtractStreamEventsJob` does (5-minute parts, speaker names, `context`) to `storage/app/private/prompt-eval/` and run `docker compose exec -T worker python3 /worker/prompt_eval.py /var/www/html/storage/app/private/prompt-eval/<file>.json`. Current prompt (CUDA, 2026-10-09): 6/6 story moments, 0 noise events, 0 events on the routine/chat-only chunk; on 20 real parts of stream 66 (Jeremy Frieser, 2:20-3:40, the district swap talks with Morrog): 17 events, 7 whole-part events skipped, no made-up places, ~15 s per part, and a storyline without repeats (`storage/app/private/prompt-eval/stream66.json`).
   - A chunk whose model output is unusable (worker HTTP 422 → `InvalidModelOutputException`) is skipped, and the job completes with a note in `event_extraction_error`. An unreachable or crashing worker (other errors) fails the job.
   - Events are collected in memory and replace the stream's previous events in one transaction at the end, so re-runs and queue retries never duplicate, and a failed run keeps the previous result.

Key cross-language contracts:
- A worker in the dev stack reads videos from the **same storage directory**, mounted read-only (`WORKER_STORAGE_ROOT`). `video_path` must be a relative path inside that root; `resolve_stream_file` rejects path traversal. A worker without the file downloads `video_url` (`resolve_input`).
- Event types are defined twice and must stay in sync: `EVENT_TYPES` in `worker/event_extractor.py` and `$types` in `ExtractStreamEventsJob::validateEvent` (plus their Dutch labels in `eventTypeLabel`, `resources/js/composables/streamStatus.ts`). Both sides check that segment indexes are relative to the chunk and that timestamps fall inside the chunk.
- Both jobs use `lockForUpdate` + a `*_status === 'processing'` guard so they are idempotent, and they set the status to `failed` with the error message in their `catch`/`failed()`. `markAsProcessing` saves through a locked copy, so `handle()` must `$stream->refresh()` afterwards. Otherwise a later `completed`/`failed` save is skipped as "unchanged" and the stream stays stuck on `processing`.
- Worker HTTP contract: `/extract-events` (`{events, summary}`) and `/summarize-story` (`{summary, players}`) always answer with a complete JSON response (400 bad request, 422 unusable model output, 500 crash). `/transcribe` validates the request before streaming NDJSON, and errors after that are `{"type":"error"}` lines. Never write a body without a status line: curl rejects it as "HTTP/0.9".
- `queue:work` and the Python worker keep code in memory. After changing jobs/services or `worker/*.py`, run `make restart` (or `make worker-restart`). Both run `up -d` first: `docker compose restart` alone keeps the environment a container was created with, so after changing `.env` the queue kept analysing with old `EVENT_*` values (90 s parts) until it was recreated. **Only when no job runs**: a restart kills a running transcription, analysis or download, and its stream stays on `processing` (the job's guard then also blocks the retry). `make start/stop/restart/worker-up/worker-restart` refuse while a stream is `processing` (`make idle`); `FORCE=1` goes ahead. A job that saved nothing for `Stream::STALLED_AFTER_MINUTES` (10) while `processing` counts as killed (`Stream::isStalled()`, shown as “Lijkt vastgelopen”): its button (“Opnieuw starten”) queues it again. Transcription and download save progress every few seconds, and event extraction saves its progress after every chunk (`event_extraction_chunks_done`/`_total`, shown as a progress bar with an ETA from the average pace per chunk). The job guards also skip a stream that is already `completed`, so a late retry of the killed attempt (it stays in Redis' `queues:default:reserved` until its reservation expires) does not redo finished work. Re-runs must therefore always set the status to `queued` first, as the buttons and `stream:transcribe` do: a job only starts from `Stream::STARTABLE_STATUSES` (queued, waiting, or `failed` for its own retry), so tests that call `handle()` directly use `markQueued()` first.
- **Cancelling** (`POST /streams/{id}/cancel/{task}`, task = `transcription`/`event_extraction`/`video_download`, `App\Services\StreamJobCanceller`; ✕ Annuleren in the stream table and on the stream page): a queued, waiting or stalled job is cancelled at once by putting its status back (the job then skips itself when it starts). A running job gets `{task}_cancel_requested_at`; the job checks it (`throwIfRequested`, throws `JobCancelled`): transcription every 2 s in the worker's event callback, analysis before every chunk, download every 2 s while yt-dlp runs (SIGTERM, partial files removed). `restore()` puts the status back to what the stored result says: `completed` when old segments/events exist (they are only replaced when a run completes), else `pending`. Closing the NDJSON connection stops the Python worker too: `write_event` turns the broken pipe into `ClientGone`, which is re-raised past the Whisper/diarization error handling and kills FFmpeg.
- **GPU model swapping** (`worker/model_manager.py`): the laptop GPU has 8 GB of VRAM and cannot hold Whisper (`large-v3-turbo`, ~2 GB) and Qwen (~6.1 GB, `unsloth/Qwen3-8B-bnb-4bit`, pre-quantized) together. `ModelManager` keeps at most `WORKER_MAX_LOADED_MODELS` (default 1; 2 on the 16 GB RTX 4080) loaded and unloads the least recently used one when another is requested. The model stays loaded between requests (so the chunk requests of one extraction do not reload it) and each model is unloaded after `WORKER_MODEL_IDLE_SECONDS` (default 600) unused. A lock is held while a model is in use: transcription holds Whisper for the whole stream, and an event request waits. Measured: Whisper loads in ~1-2 s, Qwen in ~11-18 s, inference takes ~5-8 s per chunk. Never keep references to a model outside `MODELS.use(...)`, or the VRAM is not freed.
- Model caches persist in `worker/.cache` (Whisper, bind mount) and the `event_model_cache` volume (`HF_HOME`). `worker/.dockerignore` keeps them out of the image. Changing `worker/requirements.txt` triggers a full rebuild of the ~7 GB worker image (pip + layer export, 10+ minutes).
