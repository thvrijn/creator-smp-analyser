# AGENTS.md

This file provides guidance to AI coding agents (Codex, Claude Code, etc.) when working with code in this repository.

## Project

CreatorSMP4 turns Minecraft livestream recordings (Dutch-language, "Creator SMP 4") into recaps: upload a stream video → transcribe it with faster-whisper → extract notable events with a local LLM (Qwen3-8B) → (planned) timeline and video builder.

**Language:** everything the user sees is Dutch: UI text, flash messages, error messages we write (also the worker's errors sent to the app) and the generated event titles/descriptions. Code, comments, logs and CLI output stay English. Minecraft/game terms (Nether, bastion, pickaxe…) may stay English. Internal keys stay English with Dutch labels in the UI (status values, event `type` via `eventTypeLabel` in `streamStatus.ts`). The Laravel locale is fixed to `nl` in `config/app.php`; `lang/nl` only holds the validation rules and pagination labels the app uses.

## Data safety (from README — mandatory)

Never wipe or reset the database or volumes without explicit permission: no `migrate:fresh`, `db:wipe`, `docker compose down -v` or similar. Existing players, streams, transcripts and uploads must be kept. Add new migrations instead of editing old ones, and check existing data before deleting records, tables or volumes.

**Tests use a separate database:** the feature tests use `RefreshDatabase`, which wipes the database it runs against. `phpunit.xml` points them at `creatorsmp4_test` (in the same Postgres container) with both `<server>` and `<env>` set with `force="true"`. Both are needed: Docker injects `DB_*` as real environment variables, and Laravel reads `$_SERVER` first, so `<env>` alone silently falls back to the dev database. Don't remove these overrides. The same goes for `CACHE_STORE` and `QUEUE_CONNECTION` (Docker sets redis): without `force`, tests shared the dev Redis cache and could push jobs to the dev queue. If the Postgres volume is ever recreated, recreate the test database with `docker compose exec -T postgres psql -U creatorsmp4 -d creatorsmp4 -c "CREATE DATABASE creatorsmp4_test OWNER creatorsmp4"`.

## Commands

Everything runs in Docker Compose. Use the Makefile (`make help`):

- `make start`: the one command to get a working stack. It runs `up -d --build --wait` (layer cache, so it only rebuilds what changed), creates `creatorsmp4_test` if missing (`make test-db`), downloads the Whisper and event models into their caches (`make models`), and runs `scripts/check.sh` (`make check`: postgres, test DB, redis, migrations, app, queue, worker `/health`, GPU/CUDA). Keep this working whenever setup steps are added. `make stop` brings the stack down. The `app` container runs `migrate --force`, `artisan serve` (:8000) and Vite dev (:5173, HMR) together.
- `make test`: Laravel feature tests (`php artisan test` in `app`). Run one test with `make test-filter FILTER='--filter=TranscriptionJobTest'` (or `--filter=test_method_name`).
- `make prompt-eval`: score the event-extraction prompt with the real model (see Architecture).
- `make worker-test`: all Python worker tests (`unittest discover` over `worker/test_*.py`). Run one file with `docker compose exec -T worker python3 -m unittest /worker/test_model_manager.py`.
- `make artisan CMD='...'`, `make migrate`, `make build` (Vite production build), `make shell`.
- `make logs-app` / `logs-queue` / `logs-worker`.
- `make remote-worker` (on a laptop/pc/Mac that works for the app elsewhere, e.g. the Pi): creates `worker/.env` from `worker/.env.example` on the first run, then builds and starts only the worker (`docker-compose.worker.yml`; native on macOS), downloads the models and checks that it checked in. `make remote-worker-stop` / `remote-worker-logs`. Don't run it next to the dev stack's own worker on the same GPU.
- `make user` (`php artisan user:create [--username= --name= --password=]`): create a login account, or set a new password for an existing username. There is no registration page. `AdminUserSeeder` (also called by `DatabaseSeeder`) adds the default admin account once and never overwrites it, so a changed password is kept.
- `php artisan workers:list [--online]`: the registered workers and what they are doing.
- **Production / deploy** (setup in `DEPLOY.md`, same approach as `../uitzet-tracker-new`): the Raspberry Pi runs `docker-compose.prod.yml` from the checkout `/opt/docker/apps/creator-smp-analyser` (app on FrankenPHP as container `creatorsmp4`, port 8000 on the external Docker network `proxy` of the Pi's reverse proxy, no published ports; `QUEUE_WORKERS` queue processes; postgres; redis; no worker). The image comes from `docker/php/Dockerfile.prod` (assets built in a Node stage, `--no-dev`, `php artisan optimize` in `docker/php/entrypoint.prod.sh`) and is built on the Pi. `.github/workflows/ci.yml`: Laravel tests (Postgres service) and worker tests on GitHub's runners for every push/PR; a push to master then runs on the Pi's self-hosted runner (`[self-hosted, linux, ARM64]`, its own runner for this repo), which fetches with the run's token and calls `scripts/deploy.sh <sha>`. `deploy.sh` checks out the commit, builds the image while the old version runs, waits until no stream is `processing` (`DEPLOY_WAIT_MINUTES`, `FORCE=1`), backs up the database to `backups/` (kept: `DEPLOY_KEEP_BACKUPS`), migrates, runs `AdminUserSeeder` (only that seeder: `DatabaseSeeder` adds development data), and starts the new containers with `--wait`. It never removes volumes. Pull requests must never run jobs on the self-hosted runner (the repo is public). Keep the image building (`docker build -f docker/php/Dockerfile.prod .`) when adding PHP extensions or system tools, and keep `.env.production.example` in sync with new settings. The app trusts `X-Forwarded-*` from any proxy (`bootstrap/app.php`), because only the reverse proxy reaches it on the Pi.
- `make artisan CMD='db:seed --class=CreatorSmpPlayerSeeder'`: adds the 90 Creator SMP 4 players from creatorsmp.nl/spelers, with their Twitch logins and their photos downloaded from its CDN (source: `https://aap.creatorsmp.nl/api/events/{season 4 event id}/players`, `socials.twitchUrl`). Safe to re-run: existing players, photos and Twitch logins are kept, only missing ones are filled in. `DatabaseSeeder` calls it too.
- `php artisan stream:transcribe {id} [--sync]`: queue a transcription (or run it inline to debug) for an existing stream.
- Pint (`vendor/bin/pint`) is installed as a dev dependency. There is no JS lint or typecheck script.

## Architecture

Docker services: `app` (PHP 8.3 + Node: Laravel 12 + Inertia/Vue 3/TS, `PHP_CLI_SERVER_WORKERS=4`), `queue` (`queue:work redis`, timeout 3600s, `QUEUE_WORKERS` replicas, default 3, so a transcription on one worker does not hold up a job for another), `postgres`, `redis` (cache + queue), and `worker` (a Python HTTP server on :8001 that needs an NVIDIA GPU through the Container Toolkit; for CPU, set `WHISPER_DEVICE=cpu`, `WHISPER_COMPUTE_TYPE=int8`, `EVENT_DEVICE=cpu`).

**macOS** (detected by the Makefile, so always use `make` there): Docker cannot reach the Apple GPU, so the worker runs natively. The Makefile exports `COMPOSE_FILE=docker-compose.yml:docker-compose.mac.yml`, which leaves `worker` out of Docker; the native worker checks in as `mac-local` with `http://host.docker.internal:8001` (or with the settings in `worker/.env` when that exists). `scripts/worker-mac.sh` runs it from `worker/.venv` (built with `uv` from `worker/requirements-mac.txt`; `brew install ffmpeg uv` if missing), with Whisper on the CPU (int8) and Qwen on Metal through MLX (`EVENT_DEVICE=mlx`, `mlx-community/Qwen3-8B-4bit`). The worker logs to `storage/logs/worker.log` (`make logs-worker`), and `make restart`/`stop` restart/stop it too.

**Workers (registry):** the app never has a fixed worker URL. Every worker (the dev stack's `local-docker`, the native Mac worker, or a remote laptop/pc via `make remote-worker`) runs `worker/registration.py`: every 15 s it POSTs name, own URL (`WORKER_PUBLIC_URL`), backend/GPU/VRAM, capabilities (`WORKER_CAPABILITIES`, default `transcribe,extract`), priority (`WORKER_PRIORITY`, default cuda 100, mlx 50, cpu 10) and busy to `POST /api/workers/heartbeat` (`routes/api.php`, Bearer `WORKER_TOKEN`, checked by `VerifyWorkerToken`), and `POST /api/workers/offline` on SIGTERM/SIGINT. Without `WORKER_APP_URL` it does not check in. `workers` table / `App\Models\Worker`: online = heartbeat within `WORKER_ONLINE_SECONDS` (45). `App\Services\WorkerPool::claim($task, $stream)` locks and claims the best free, online, enabled worker with that capability (priority, then VRAM); one task per worker; `release()` in the jobs' `finally`. A worker the app cannot reach is marked offline (`markUnreachable`), so the retry picks another. A heartbeat with `busy=false` releases a claim older than `WorkerPool::STALE_CLAIM_SECONDS` (a killed queue job). Without a free worker a job sets the status to `waiting` ("Wacht op worker"; transcription stage `waiting_for_worker`), touches the stream and `release()`s itself every `WORKER_WAIT_SECONDS` (30): the jobs use `retryUntil()` (7 days, trait `App\Jobs\Concerns\WaitsForWorker`) plus `maxExceptions`, so waiting never uses up attempts. `waiting` counts as active in the controllers and `isStalled()` (a waiting stream that is not touched for 10 min lost its job). Audio: the app sends both `video_path` and `video_url`, a temporary signed route (`/api/worker-files/streams/{id}`, `signed:relative`, 12 h) prefixed with `WORKER_APP_URL`; a worker with the shared storage reads the file, any other downloads it into a temp file (stage `downloading_audio`, removed afterwards). The worker's own endpoints require the Bearer token when `WORKER_TOKEN` is set (401). `make start` generates `WORKER_TOKEN` in `.env` (`make worker-token`); a remote worker needs the same token in `worker/.env`. Settings (`/settings`) lists the workers (shared Inertia prop `workers`), can disable (`enabled`) or forget one; the header shows how many are online. Networking between the Pi and the workers: Tailscale (same names at home and away).

**Processing pipeline (spans PHP + Python):**

1. `StreamController@store` saves the uploaded video to the default disk (`storage/app/private`, max size from `config/streams.php`).
2. `POST /streams/{id}/transcribe` dispatches `App\Jobs\TranscribeStreamJob`. `App\Services\TranscriptionWorker` POSTs `{stream_id, video_path, video_url, ranges}` to the claimed worker's `/transcribe` and reads back a **streaming NDJSON** response. Event types: `duration`, `stage`, `progress`, `segment`, `speakers`, `warning`, `completed`, `error` (stages: `downloading_audio`, `extracting_audio`, `transcribing`, `diarizing`). The job throttles progress writes into the `transcription_*` telemetry columns on `streams` (stage, progress, processed/duration seconds, ETA), then replaces all `transcript_segments` in one transaction.
   - **Speakers (diarization, `worker/diarization.py`):** after Whisper, pyannote (`pyannote/speaker-diarization-3.1`, `pyannote.audio` 3.4; 4.x needs torch 2.8) runs over the same extracted 16 kHz chunks, kept back to back (`read_audio` pads/cuts each to its nominal length, so `_audio_start` = chunk's place in the transcribed parts + Whisper time). Each segment gets the speaker with the most overlap (`transcript_segments.speaker`, null = none). Speakers are numbered by speaking time, so 0 speaks the most: in a player's own stream almost always the streamer (the UI shows the player's name for 0, "Spreker n" for the others). It only says who speaks when, not who they are. The `speakers` event carries `segment_speakers` (indexed like the worker's `segment` events, so `TranscriptionWorker` keys segments by that index) and per speaker its speaking time and voice embedding, stored as `streams.transcription_speakers` for matching voices to players later (step 2). It is off without `HF_TOKEN` (gated models: accept hf.co/pyannote/speaker-diarization-3.1 and hf.co/pyannote/segmentation-3.0); a failure only sends a `warning` and keeps the transcript without speakers. pyannote is a third model in `ModelManager` (`diarization`), loaded after Whisper is released. Measured on the RTX 5060 laptop: a 3 h stream diarizes in ~6 min at ~2.9 GB RAM (20 min of audio: ~45 s). Two things keep that working: `MALLOC_MMAP_THRESHOLD_` in `worker/Dockerfile` (without it glibc never returned pyannote's batch tensors and a 3 h stream grew past 6 GB and was OOM-killed), and `DIARIZATION_MAX_CLUSTER_EMBEDDINGS` (clustering memory grows with the square of the embeddings). pyannote 3.4's checkpoints need `allow_checkpoint_classes()` under torch>=2.6 (`weights_only`). The event prompt does not use speakers yet. **Corrections** (`App\Services\StreamSpeakers`, `SpeakerController`, the speaker bar and per-segment speaker menu in the Transcript tab): a speaker can be named after a player or a free label (`stream_speakers`, unique per stream+speaker; a row with a player is a confirmed voice for step 2), merged into another speaker (segments move, `transcription_speakers` adds up the speaking time and averages the embeddings by speaking time, the name moves along when the target has none), and a single segment can move to another speaker, a new speaker number or none. A new transcription deletes the stream's `stream_speakers` (new numbers). A row with neither player nor label means "unknown, don't match". **Voice matching across streams (step 2, `App\Services\VoiceProfiles`):** a player's profile is the normalised mean of their known voices (speakers named after them by hand, plus speaker 0 of their own streams unless named otherwise; speakers under `VOICE_MIN_SECONDS` are skipped). An unnamed speaker (not 0) is shown as the player whose profile is closest (cosine) when ≥ `VOICE_MATCH_THRESHOLD` and `VOICE_MATCH_MARGIN` ahead of the next, each player once per stream and never a player already in it (source `matched`, shown with a `?` and a "✓ Klopt" button that confirms it). The profiles are cached forever and forgotten by model events (`StreamSpeaker` saved/deleted, `Stream` `transcription_speakers` changed or deleted, `Player` deleted) and in `StreamSpeakers::name()`. The default threshold (0.6) is not measured on real streams yet: `php artisan voices:evaluate` compares all known voices across streams and prints per threshold how many same-player pairs pass and how many different players get mixed up.
3. `POST /streams/{id}/extract-events` dispatches `ExtractStreamEventsJob`. It splits the segments into time windows that overlap (`EVENT_CHUNK_SECONDS`/`EVENT_CHUNK_OVERLAP_SECONDS`, see `config/services.php`), POSTs each chunk to `worker /extract-events` (plain JSON), validates again, dedupes by type+title+segment IDs, and stores `events` linked to segments through the `event_transcript_segment` pivot.
   - Validation rules (agreed with the user), applied on both sides: an invalid event is skipped and logged, never stored, and the rest of the chunk is kept. Event `start_time`/`end_time` are always derived from the referenced segments, never taken from the model (the prompt no longer asks for timestamps). An event with more than `EVENT_MAX_SEGMENTS` (default 12) segments is a chunk summary and is skipped.
   - Dedupe across overlapping chunks: events sharing at least half of the smaller event's segments are the same moment, whatever the title or type. The most confident one is kept.
   - The prompt (`SYSTEM_PROMPT` in `worker/event_extractor.py`) targets an SMP with ~90 streamers who each stream their own perspective and meet each other. `type` is optional: the model uses `other` unless a type clearly fits, and the UI hides `other`. Titles must name the other players involved. Measure prompt changes with `make prompt-eval` (synthetic Dutch SMP chunks with known moments, plus a filler-only chunk; uses the GPU and restarts the worker). Current prompt (Dutch titles, MLX on macOS): 11/12 moments, 4 extra events, 0 events on filler. The earlier English version scored 12/12 with 1 extra on CUDA.
   - A chunk whose model output is unusable (worker HTTP 422 → `InvalidModelOutputException`) is skipped, and the job completes with a note in `event_extraction_error`. An unreachable or crashing worker (other errors) fails the job.
   - Events are collected in memory and replace the stream's previous events in one transaction at the end, so re-runs and queue retries never duplicate, and a failed run keeps the previous result.

Key cross-language contracts:
- A worker in the dev stack reads videos from the **same storage directory**, mounted read-only (`WORKER_STORAGE_ROOT`). `video_path` must be a relative path inside that root; `resolve_stream_file` rejects path traversal. A worker without the file downloads `video_url` (`resolve_input`).
- Event types are defined twice and must stay in sync: `EVENT_TYPES` in `worker/event_extractor.py` and `$types` in `ExtractStreamEventsJob::validateEvent` (plus their Dutch labels in `eventTypeLabel`, `resources/js/composables/streamStatus.ts`). Both sides check that segment indexes are relative to the chunk and that timestamps fall inside the chunk.
- Both jobs use `lockForUpdate` + a `*_status === 'processing'` guard so they are idempotent, and they set the status to `failed` with the error message in their `catch`/`failed()`. `markAsProcessing` saves through a locked copy, so `handle()` must `$stream->refresh()` afterwards. Otherwise a later `completed`/`failed` save is skipped as "unchanged" and the stream stays stuck on `processing`.
- Worker HTTP contract: `/extract-events` always answers with a complete JSON response (400 bad request, 422 unusable model output, 500 crash). `/transcribe` validates the request before streaming NDJSON, and errors after that are `{"type":"error"}` lines. Never write a body without a status line: curl rejects it as "HTTP/0.9".
- `queue:work` and the Python worker keep code in memory. After changing jobs/services or `worker/*.py`, run `make restart` (or `make worker-restart`). **Only when no job runs**: a restart kills a running transcription, analysis or download, and its stream stays on `processing` (the job's guard then also blocks the retry). `make start/stop/restart/worker-up/worker-restart` refuse while a stream is `processing` (`make idle`); `FORCE=1` goes ahead. A job that saved nothing for `Stream::STALLED_AFTER_MINUTES` (10) while `processing` counts as killed (`Stream::isStalled()`, shown as “Lijkt vastgelopen”): its button (“Opnieuw starten”) queues it again. Transcription and download save progress every few seconds, and event extraction saves its progress after every chunk (`event_extraction_chunks_done`/`_total`, shown as a progress bar with an ETA from the average pace per chunk). The job guards also skip a stream that is already `completed`, so a late retry of the killed attempt (it stays in Redis' `queues:default:reserved` until its reservation expires) does not redo finished work. Re-runs must therefore always set the status to `queued` first, as the buttons and `stream:transcribe` do: a job only starts from `Stream::STARTABLE_STATUSES` (queued, waiting, or `failed` for its own retry), so tests that call `handle()` directly use `markQueued()` first.
- **Cancelling** (`POST /streams/{id}/cancel/{task}`, task = `transcription`/`event_extraction`/`video_download`, `App\Services\StreamJobCanceller`; ✕ Annuleren in the stream table and on the stream page): a queued, waiting or stalled job is cancelled at once by putting its status back (the job then skips itself when it starts). A running job gets `{task}_cancel_requested_at`; the job checks it (`throwIfRequested`, throws `JobCancelled`): transcription every 2 s in the worker's event callback, analysis before every chunk, download every 2 s while yt-dlp runs (SIGTERM, partial files removed). `restore()` puts the status back to what the stored result says: `completed` when old segments/events exist (they are only replaced when a run completes), else `pending`. Closing the NDJSON connection stops the Python worker too: `write_event` turns the broken pipe into `ClientGone`, which is re-raised past the Whisper/diarization error handling and kills FFmpeg.
- **GPU model swapping** (`worker/model_manager.py`): the laptop GPU has 8 GB of VRAM and cannot hold Whisper (~0.6 GB) and Qwen (~6.1 GB, `unsloth/Qwen3-8B-bnb-4bit`, pre-quantized) together. `ModelManager` keeps at most `WORKER_MAX_LOADED_MODELS` (default 1; 2 on the 16 GB RTX 4080) loaded and unloads the least recently used one when another is requested. The model stays loaded between requests (so the chunk requests of one extraction do not reload it) and each model is unloaded after `WORKER_MODEL_IDLE_SECONDS` (default 600) unused. A lock is held while a model is in use: transcription holds Whisper for the whole stream, and an event request waits. Measured: Whisper loads in ~1-2 s, Qwen in ~11-18 s, inference takes ~5-8 s per chunk. Never keep references to a model outside `MODELS.use(...)`, or the VRAM is not freed.
- Model caches persist in `worker/.cache` (Whisper, bind mount) and the `event_model_cache` volume (`HF_HOME`). `worker/.dockerignore` keeps them out of the image. Changing `worker/requirements.txt` triggers a full rebuild of the ~7 GB worker image (pip + layer export, 10+ minutes).

**Login:** every web route except `/login` is behind the `auth` middleware (`routes/web.php`); guests are redirected to `/login` and back to the page they asked for afterwards (`AuthController`, session guard with "Ingelogd blijven" = remember me, 5 attempts per username+IP before a wait). Users log in with a username, stored lowercase so case does not matter (the e-mail column is optional). Accounts live in `users` (`App\Models\User`) and are made with `user:create`. Not behind the login: the worker API (`routes/api.php`, Bearer `WORKER_TOKEN`), the signed worker-file URLs and `/up`. The shared Inertia prop `auth.user` (with `is_admin`) feeds the profile menu in the header (Profiel en wachtwoord, Uitloggen). `/profile` (`ProfileController`) changes your own password (current password required, min 8, confirmed); it also replaces the remember token and deletes the user's other sessions, so other devices are logged out. **Admin:** there is exactly one admin, recognised by `User::ADMIN_EMAIL` (`isAdmin()`; there is no admin flag, and accounts created in the app never get an e-mail address, so nobody else can become admin). Only the admin can open `/users` (`UserController`, `EnsureUserIsAdmin` middleware, 403 for others; the sidebar shows "Gebruikers" only to the admin) to create and remove accounts; the admin account itself cannot be removed. There is no sign-up. `user:create` on the server stays as the fallback for whoever has shell access (e.g. a forgotten admin password). **Activity log** (`activity_logs`, `App\Services\ActivityLogger`, admin-only page `/activity`): the `LogActivity` web middleware logs every non-GET request of a logged-in user to a route in `ActivityLogger::ACTIONS` (route name → Dutch description), with the route's model as subject (name copied, so it survives deletion) and the flash message as result (`error` flash = failed). Requests that only fail validation are not logged; request input is never stored. `AuthController` logs logins, logouts and failed attempts (with the tried username). The same action on the same subject within 2 minutes adds to the last entry (`count`), e.g. nudging a clip. Add new user actions to `ACTIONS`. Feature tests act as an unsaved `User` by default (`Tests\TestCase::$signedIn`); `AuthenticationTest` turns that off.

**Frontend:** Styling follows creatorsmp.nl in dark mode (all in `resources/css/app.css`): background `#0a0a0f`, surface `#111118`, cards `#1a1a24`, neutral greys with hue 240 (not blue), gold accent `#e8a011` (hover `#f5b020`, primary buttons gold with dark text), a faint dark-red "hardcore" glow, Montserrat for text and Space Grotesk for headings, dark scrollbars. Status colours keep their meaning (green/red); encounter events use Twitch purple. Inertia pages are in `resources/js/Pages/**` (resolved by name in `app.ts`), and controllers return `Inertia::render(...)` with props mapped explicitly. `/dashboard` shows a card per player (`PlayerController@dashboard`, stats from `Player::scopeWithStreamStats`). A card links to `/players/{id}` (`Players/Show`), which lists that player's streams. A stream row (shared `StreamsTable`) opens `/streams/{id}` (`Streams/Show`): stream status and actions, with **Events | Transcript** tabs (paginated, searchable transcript). The tab lives in the URL (`?tab=events|transcript`); without it, `event`, `search` or `page` open the Transcript tab. `?event={id}` selects an event, jumps to the transcript page with its first segment, and highlights its segments (unless `page` is given explicitly). With a media file the page has an audio player (`GET /streams/{id}/audio`, `response()->file`, so Range requests seek): ▶ on a segment or event plays from its start (segment and event times are file times), and the segment playing on the current transcript page lights up and is followed. The old `/streams/{id}/transcript` 301-redirects there. Status labels, button logic and status polling are shared in `resources/js/composables/streamStatus.ts`. The old dashboard lives on as `/overview`. Player photos (`players.photo_path`, JPG/PNG/WebP up to 2 MB, no SVG) live on the default disk under `players/` and are served by `GET /players/{id}/photo`, not a `storage:link` symlink. `Player::photoUrl()` adds `?v=updated_at`, so the response can be cached forever. The player form (`Components/PlayerFormModal.vue`, used on `/players` and the player page) sends files as a POST with `_method=put`, because PHP does not parse multipart PUT. An update redirects `back()`. Every avatar goes through `Components/PlayerAvatar.vue` (photo, or a coloured initial). On `/players` a row opens the player page. `players.twitch_login` is the channel name in `twitch.tv/<login>`, which often differs from the display name. The player page links to it, and the form turns a pasted channel URL into the login. **VOD sync** (`App\Services\TwitchVodSync`, `TwitchVodController`; buttons on the player page and the dashboard) runs synchronously: one Twitch call looks up all channels, then `Http::pool` fetches each channel's past broadcasts (`type=archive`, one page of 100). Every VOD since `TWITCH_VODS_SINCE` (season start, default 2026-10-04) becomes a stream with `source=twitch` and a unique `twitch_video_id`, **without media. **Audio ophalen** (`POST /streams/{id}/download-audio` → `DownloadVodJob`, on the normal queue) downloads the VOD's whole audio-only rendition with yt-dlp (`ba/worst`, ~90 MB/hour, yt-dlp's own HLS downloader) and keeps the file whole, so file time = VOD time (`video_offset_seconds` 0). It stores the parts in the Twitch category `TWITCH_CATEGORY` (CreatorSMP, from the VOD's chapters that yt-dlp prints) during the server's opening hours (`App\Services\ServerHours`, 14:00-00:00 Dutch time by default) as `streams.transcription_ranges` (`[[start, end], ...]` seconds, null = everything), so another game in between is left out. `TranscriptionWorker` sends them as `ranges` to `/transcribe`, and the worker transcribes only those parts (`transcription_spans`, clipped and merged), with segment times in file time and duration/progress counting only the parts. This replaced cutting, which needed a re-encode (~5 min per 5 h) and could only keep one span. A VOD without such a part fails with a message and its file is removed. yt-dlp's `--progress-template` prints `progress i/n` per fragment on stdout; the job saves `video_download_progress` at most every 2 s, and the stream table polls every 3 s while a download runs. The sync already skips VODs entirely outside the opening hours (the Twitch API has no category per VOD). Don't use `--download-sections` for Twitch: ffmpeg seeking straight into Twitch's HLS playlist hangs (from the start it works). Don't derive play windows from creatorsmp.nl's stats history either: it keeps about one point per player per day (last leave and total `play_time`), not when they joined. The file is stored as the stream's `video_path` (mime `audio/mp4`), so transcription works as for an upload. `video_offset_seconds` is where the file starts in the VOD (VOD time = offset + segment time). A failed download removes its partial files. Video clips are meant to be fetched later, only for chosen moments, while the VOD still exists (60 days for Partners). yt-dlp and ffmpeg are in the PHP image (`docker/php/Dockerfile`, checked by `make check`). The root `.dockerignore` keeps `worker/` (gigabytes of venv and models) and `.env` out of the PHP image. A re-sync updates `ended_at` but keeps a title changed in the app. The sync also asks Twitch which channels are live (`helix/streams`): the VOD of a stream that is still live gets `ended_at = null` (shown as Live), and its audio is refused until a re-sync after the stream ended, because yt-dlp would follow a live VOD from its live edge for hours and miss the start. It needs `TWITCH_CLIENT_ID`/`TWITCH_CLIENT_SECRET` (a Twitch app, client credentials). The app token is cached and replaced once on a 401. The stream table (statuses, live polling of `/streams/{id}/transcription-status`, Transcribe/Extract/Delete buttons) is the shared `Components/StreamsTable.vue`, used by both the Streams page and the player page, and `Components/AddStreamModal.vue` is shared too. Stream props come from `App\Http\Resources\StreamResource`, and shared TS types live in `resources/js/types/streams.ts`. Stream actions redirect `back()` (fallback `/streams`), so they return to the page they were triggered from. Status values: `pending` = not started, `queued` = job dispatched, then `processing` → `completed`/`failed` (for both transcription and event extraction). **Clips** (`clips` table, `ClipController`): chosen moments for the video, made on the stream page with “＋ Clip” on an event (±15 s), “✂ Clip” on a transcript segment (1 minute) or “Hele stream”, and adjusted in the **Clips** tab (`?tab=clips&clip={id}`; ±5 s nudges are saved after 400 ms). Clip times are seconds from the stream (VOD) start, so transcript and event times get `video_offset_seconds` added. `event_id` is nulled when a re-analysis replaces the events, and the clip stays. A Twitch VOD is previewed with Twitch's embedded player (`Components/TwitchPlayer.vue`, `player.twitch.tv/js/embed/v1.js`, `parent` = the page's host, which must be localhost or HTTPS). It seeks to the clip and pauses at its end, without downloading anything. Headless Chrome renders that player white, so check it in a real browser. `/video-builder` (`VideoBuilder`) lists every clip of every player in server-time order (stream `started_at` + clip start), per day, and marks a clip that overlaps the previous one from another player as “zelfde moment”. Downloading clips in 1080p is not built yet. Timeline and Settings are still placeholder routes.

**Tests:** PHPUnit feature tests only (`tests/Feature`), using `Http::fake`, `Queue::fake` and `Storage::fake`. Python tests patch `load_whisper_model`/ffmpeg, the `diarization` functions and `EventExtractor._load`/`_generate` with fakes and swap in a fresh `ModelManager`, so no GPU is needed.
